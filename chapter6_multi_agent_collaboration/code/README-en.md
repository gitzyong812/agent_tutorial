# Chapter 6 Multi-Agent Collaboration Teaching System

Building on the digital employee system from the first five chapters, this project adds multi-agent team collaboration. Multiple digital employees can share team messages, memories, and text files while retaining their own role prompts, local execution traces, and tool permissions.

## Run

```bash
cd chapter6_multi_agent_collaboration/code
cp .env.example .env
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

Open `http://127.0.0.1:8000` in a browser. The first run creates `chatbot.db` and demonstration data. Enter an available model endpoint and key under Model Configuration, then publish a digital employee.

The script reuses an enabled chat model from the database to create and publish a fact checker, channel analyst, promotional copywriter, and content reviewer. It also writes the team members, shared memory, and `activity-brief.md`. Repeated execution does not duplicate practice data with the same names. You can specify a model with `--model-config-id`.

Open an existing conversation on the web page, click Connect Channel in the upper-right corner, expand Command Line, and copy the generated command. For example:

```bash
python -m app.cli --session-id 3 --base-url http://127.0.0.1:8000
```

The CLI joins that web session, calls `POST /api/harness/messages`, and continues using the selected digital employee and conversation context. The web interface and CLI consume the same JSON SSE stream:

```json
{
  "type": "text_delta",
  "run_id": 1,
  "payload": {"content": "回答片段"}
}
```

Event types include `text_delta`, `sources`, `trace`, `human_required`, `handoff`, `error`, and `done`. `done.payload.status` uses only `completed`, `pending`, `handoff`, and `failed`.

The default `max_tokens` for a new digital employee is `2048` and can be adjusted with `DEFAULT_AGENT_MAX_TOKENS`. ReActAgent forwards the final answer tokens from the model in real time, so the web interface and CLI use the same streaming output. Prompt text generated by the runner itself is split according to `REACT_TEXT_DELTA_CHARS`.

## Multi-Agent Team Collaboration

On the Team Collaboration page, select several published digital employees to form a team. For an ordinary message, the task planner assigns tasks according to member responsibilities. Use `@digital-employee-name` to designate a role. Tasks form a dependency graph through `depends_on`. The system executes the graph in topological batches, using at most six threads for tasks in the same batch.

Team members share message history, team memory, and UTF-8 text files. Each digital employee still uses its own role prompt, local task context, and tool configuration. A downstream task receives only its own task and the results of its dependencies. Task cards on the web page display the task number and `depends_on`. In a team session, ReActAgent does not expose write tools, `ask_human`, or skill creation, preventing parallel tasks from entering an unrecoverable human-pause state.

Dynamic planning reuses an available model bound to a team member by default, so no additional configuration is required. To select a separate model for task planning, override the default with the following environment variables:

```text
GROUP_TASK_PLANNER_MODE=llm
GROUP_TASK_PLANNER_BASE_URL=
GROUP_TASK_PLANNER_MODEL_NAME=
GROUP_TASK_PLANNER_API_KEY=
GROUP_TASK_PLANNER_MAX_TOKENS=1024
```

If team member models are unavailable, the planning model call fails, or the model returns invalid tasks, the system automatically falls back to rule-based planning using team members, `@` mentions, and dependency keywords.

## WeChat Channel

Open any existing conversation, click Connect Channel in the upper-right corner, and scan the QR code with WeChat to bind WeChat to the current session. Each binding continues to use the digital employee selected for that session. Credentials, polling cursors, and message records remain isolated across sessions.

The first version supports text messages only. WeChat requests do not call `ask_human` or expose write tools that require authorization. When a task requires a write operation, the digital employee directs the user back to the web interface. WeChat credentials are stored in the local SQLite database. This arrangement is suitable only for the chapter's single-process teaching deployment.

The QR-code login and messaging protocol follow the [CowAgent WeChat channel](https://docs.cowagent.ai/channels/weixin). Related timeouts and service addresses can be adjusted through the `WEIXIN_*` settings in `.env`.

## Human Collaboration and Permissions

A new or first-upgraded ReActAgent binds two removable built-in tools by default:

- `ask_human(question, input_type)`: Pauses the current loop when essential information cannot be inferred, or when the user has explicitly agreed to discuss a focused question that materially affects the result. By default, it can be called at most twice per run. `input_type` supports `confirm` and `text`, and the limit can be adjusted through `MAX_HUMAN_REQUESTS_PER_RUN`.
- `handoff_to_human(summary, missing_information, requested_action)`: Ends the current run when the task cannot continue and returns structured handoff information.

There are three tool policies:

- `read` executes automatically.
- `write` displays an authorization card in the current conversation bubble. The same ReAct loop continues after approval or rejection.
- `restricted` rejects the operation immediately and returns the restriction to the model as a tool observation.

Before executing an approved write operation, the system rechecks the tool binding, risk policy, parameter Schema, URL, Method, and request headers. An earlier authorization cannot be reused after the configuration changes.

## System Monitoring

The System Monitoring page manually loads `GET /api/monitoring/overview`. Key runtime metrics appear at the top, with tabs for recent runs and redacted events below. Both lists are paginated in reverse chronological order and support filtering by digital employee and date. The page does not poll or provide approval lists or business tickets.

## Migrating an Older Database

If an older database contains the example service tickets, run:

```bash
python scripts/migrate_remove_service_tickets.py --database chatbot.db
```

The script first backs up SQLite, then removes the `service_tickets` table, old built-in tools, and skill bindings. Incomplete older authorizations are marked as failed. The script is idempotent and preserves user-defined HTTP tools with the same names.
